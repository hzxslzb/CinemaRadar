# 14 · 扩展方案与技术债

本章全部为后续建议，除明确引用“当前实现”外，不应视为已上线能力。优先级依据影响范围与源码风险判断，不是实测事故统计。

## 1. 演进原则

1. 优先保证订阅正确性和提醒语义，再增加刷新频率。
2. 保持每台设备独立可用；新功能不应无意中让电脑成为手机后端。
3. 在客户端放可公开配置，在可信服务端放票务私钥和支付事务。
4. 能通过小接口替换的能力先抽象接口，不需要为了简单改动重写整个框架。
5. 每个方案附可验证的行为与测试，不用设计图代替实现。

## 2. 高优先级技术债

| 编号 | 当前缺口 | 建议与验收标准 |
| --- | --- | --- |
| TD-01 | 影院刷新缺少请求归属校验 | 记录 generation/影院 key；旧响应不能覆盖新影院状态；增加快切交错测试 |
| TD-02 | 一个影院失败终止整轮 | 每影院独立结果与错误；A 失败时 B 仍能检查并提交 |
| TD-03 | SharedPreferences 全列表跨环境写入 | 引入事务存储/版本校验；删除订阅不能被旧 Worker 写回复活 |
| TD-04 | 通知发送与基线落盘不同步 | outbox/投递状态；崩溃重启不无界重复且不静默丢失新增 |
| TD-05 | 恢复前台文案强于实现 | 明确“立即补查”或“等待周期”的产品语义，再统一代码、测试和文案 |
| TD-06 | macOS 删除路径未统一重配 Timer | 所有订阅变更走同一调度同步；最后订阅删除后不再后台刷新 |
| TD-07 | 系统通知点击仅有 payload | 实现运行中/冷启动路由；点击后定位目标影院和影片 |
| TD-08 | 最新批次覆盖旧未读批次 | 根据产品选择有限队列/聚合，确保关闭只影响指定批次 |

## 3. 调度器独立化

当前控制器的 `_scheduledRefresh` 将“刷新当前浏览影院”和“检查订阅”绑定，macOS 后台可能多查一个无订阅影院。

建议引入明确的 trigger：startup、foregroundTimer、manual、resume、backgroundWorker。每类 trigger 配置是否刷新当前影院、是否复用快照、是否立即执行以及节流时间。

一个可能的接口是：

```dart
// 设计示例，当前仓库未提供此接口。
abstract interface class RefreshCoordinator {
  Future<void> refreshVisibleCinema();
  Future<MonitorResult> checkSubscriptions();
  Future<void> onResume();
  Future<void> synchronizeSchedule();
}
```

验收应包括：无订阅取消后台、前台 3 分钟不变、恢复前台不与上一轮重叠、macOS 只检查订阅、Android 使用唯一周期任务。

## 4. 可靠存储与 outbox

若迁移到 SQLite 或其他事务存储，应先确认 Android/macOS 及未来鸿蒙的插件支持，而不是假定所有桌面/移动插件都可用于鸿蒙。

建议按记录保存订阅、场次基线、检测轮次和通知 outbox；检测结果与基线在同一事务提交，然后异步尝试发送通知。

```mermaid
flowchart LR
    Fetch["获取快照"] --> Compute["计算差量"]
    Compute --> Tx["事务提交基线 + outbox"]
    Tx --> Deliver["独立投递系统通知"]
    Deliver --> Record["记录投递成功 / 待重试"]
```

这是建议架构。具体投递去重策略还需权衡：系统调用成功并不代表用户真正看见；崩溃窗口仍需幂等键和重试上限，不应承诺绝对 exactly-once。

## 5. 基线语义改进

当前只保存本轮 ID，导致暂时消失后恢复的场次再次提醒。可选择以下策略：

- 保存一定天数的已见历史 ID，并定期清理过期日期。
- 将“目标影片缺失”标为不确定，不立即清空已有基线。
- 区分新增、撤场、改时间、改厅、恢复售卖等事件。

每种策略都会改变提醒语义，应提供明确事件类型和测试样本。不能仅扩大 Set 而永不清理，造成存储持续增长。

## 6. 多数据源

实现新的 `ScheduleProvider` 和 `CinemaDirectoryProvider` 后，还需处理：

1. 来源名称与影院/影片/场次 ID 命名空间。
2. 外部影院映射的准确率与人工确认。
3. 时间、语言、制式与售卖状态归一化。
4. 每来源的限流、缓存、异常及授权约束。
5. 对应平台购票链接，不将来源 A 的场次 ID 塞进来源 B 的 URL。
6. 旧订阅迁移和来源不可用时的降级提示。

短期可保留现有公共模型，逐步把 `fromMaoyan` 移到适配层，让领域层不再直接依赖来源字段。

## 7. 性能演进

- 目录缓存增加 TTL/LRU，并明确跨日策略。
- 大量场次改为 Sliver/ListView 按需构建。
- 影院请求使用小并发上限和逐影院容错，避免无限 Future.wait。
- 差量与视图派生结果可按快照版本缓存，减少重复 sort。
- HTTP Client 引入明确关闭/复用周期，必要时支持请求取消。
- 将网络请求、海报下载、UI 构建分别测量，而不是只看整页耗时。

## 8. 通知与体验演进

建议把通知服务抽为接口，便于 Mock，并增加稳定通知 ID、通知点击导航、权限状态查询和投递日志。

提醒中心若支持多个未读批次，应定义容量、过期、合并、逐批关闭和跨启动恢复规则。当前单键存储不能直接当作完整历史队列使用。

主题可增加 system/light/dark 三态；筛选设置是否按影片重置或保存也应有明确交互约定。字体如需跨平台统一，应评估授权、包体、中文字符覆盖与系统缩放，而非仅设置一个不保证存在的字体名。

## 9. 授权票务接入

真实指定座位购买至少需要：授权排期与场次映射、座位图、单座/连座规则、锁座、支付单、支付回调、出票、超时解锁、退款和对账。

票务平台私钥、渠道码和交易签名不能放进可反编译客户端。可选增加独立的可信票务服务端，但基础排片/订阅仍可以保持端侧独立；这会是新增业务架构，而不是现有功能的小参数开关。

在拿到正式接口与测试环境前，不应通过仿造未授权订单请求来验证购买功能。用户的实际付款、锁座和出票必须有明确交互确认与错误补偿。

## 10. 同步与备份

可优先增加用户主动导入/导出订阅，再考虑加密云同步。需要处理 ID 集合容量、冲突、删除墓碑、版本迁移和设备间不同能力。

加入同步必须清楚解释订阅偏好发送到何处；当前“没有账户/没有云同步”的隐私说明也要随之修改。

## 11. 建议实施顺序

第一阶段：请求归属、逐影院失败隔离、恢复前台语义与 Timer 删除路径。

第二阶段：存储一致性、outbox、通知点击、可观测日志和对应测试。

第三阶段：大列表性能、缓存容量、备份导出、多批次提醒。

第四阶段：在明确授权和业务需求后接入新数据源、云同步或票务服务端。
