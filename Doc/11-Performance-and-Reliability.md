# 11 · 性能、并发与可靠性

实现入口：[Provider](../lib/data/maoyan_provider.dart)、[控制器](../lib/app_controller.dart)、[检测器](../lib/services/subscription_monitor.dart)、[本地存储](../lib/data/subscription_store.dart)。

## 1. 性能目标与现有手段

系统通过限定地域、按影院合并、目录内存缓存、场次 ID 差量和系统周期任务降低开销。没有实现全城轮询、实时座位图轮询或票价跟踪。

这些手段降低应用主动请求数，但不等于已完成电池功耗实测、长时间后台内存曲线或大规模订阅压测。

## 2. 网络请求数量

设 `K` 为不同订阅影院数，当前浏览影院为 `V`。以下只统计一次正常检测的排片 HTTP 请求，不包含目录、图片或失败重试。

| 场景 | 理想成功请求数 |
| --- | --- |
| Android Worker，无订阅 | 0 |
| Android Worker，有 K 家订阅影院 | K |
| 前台或 macOS Timer，V 也有订阅 | K |
| 前台或 macOS Timer，V 没有订阅 | K + 1 |
| 前台无订阅 | 1，仍刷新当前浏览影院 |

例如 10 部订阅都在同一家影院，Android Worker 为 1 次排片请求；若桌面当前还停留在另一家影院，控制器的周期流程通常为 2 次。

当前影院刷新失败时检测器不复用旧快照，可能再次查询同影院；上表不适用于失败路径。

## 3. 刷新频率的估算

持续前台 24 小时、每 3 分钟触发，理论为 480 轮；Android 15 分钟理论为 96 轮。实际系统调度、任务耗时、跳过重叠轮次、进程暂停和网络会改变结果。

这些数字只能用于上界量级估算，不能作为到达时间承诺或电池消耗实测结果。更精确的量化需要记录真正请求次数、执行时间、CPU/内存和系统电量数据。

## 4. 计算复杂度

每轮检测按订阅分组，构造影片索引，并为当前场次创建 ID Set。核心差量对每个场次做集合查找，期望为线性遍历。

可粗略记为 `O(U + M + S)`：U 为订阅条数，M 为所查询快照的影片数总和，S 为需比较的场次数总和。持久化每次序列化整份订阅列表，成本也随全部保存的基线 ID 数增加。

UI 的 `visibleSessions` 对可见结果排序，约为 `O(N log N)`。影院关键词过滤需要扫描所选区列表；排序匹配结果另有 `O(C log C)`，通常不需要网络请求。

## 5. 内存与缓存

| 数据 | 生命周期 | 主要风险 |
| --- | --- | --- |
| 城市/行政区/影院 Future | Provider 存活期 | 无 TTL/LRU，浏览地域多时持续增长 |
| 当前影院快照 | 控制器存活期 | 大影院多日排片增大对象数量 |
| 订阅 ID 基线 | 内存 + SharedPreferences | 整列表序列化、跨执行环境缓存 |
| 当前提醒批次 | 内存 + SharedPreferences | 单批次可能包含很多场次 |
| 海报 | Flutter 图片加载机制 | 无项目自定义离线/容量策略 |

顶部展开用 Column 直接展开所有 Tile，普通排片也用 Wrap 创建全部场次卡片。没有列表虚拟化，订阅数量没有业务上限。大量新增场次时，UI 构建开销可能高于差量算法本身。

## 6. 已有并发保护

- `_scheduledRefreshRunning`：跳过同一控制器中重叠的调度刷新。
- `loading`：避免同一控制器重复调用当前影院刷新。
- 目录缓存保存 Future：相同键的并发加载复用一个请求。
- 搜索组件部分请求检查当前城市/行政区，避免迟到成功结果覆盖新选择。
- `mounted`：避免组件销毁后的部分 setState。
- 提醒 `expectedId`：关闭时尽量避免删除另一个批次。

这些是局部保护，不构成整个应用的串行执行器。

## 7. 当前并发与可靠性缺口

| 情况 | 当前代码后果/风险 | 建议方向 |
| --- | --- | --- |
| 快速切影院且旧请求未结束 | `loading` 可能让新刷新直接返回，旧结果仍被写入 | 请求 generation + 结果归属校验 |
| 一个订阅影院请求失败 | 整轮终止，后续影院不执行 | 逐影院容错并聚合错误 |
| 已通知但后续影院失败 | 旧基线可能未保存，后续重复提醒 | 逐影院提交或 outbox |
| 前台/Worker 同时保存 | 整列表写回可能覆盖较新的修改 | 事务存储、版本检查、合并 |
| 旧通知关闭与新批次写入交错 | 先读后删仍非原子 | 条件更新或记录级状态 |
| 影片暂时从响应消失 | 基线被清空，恢复后全部算新增 | 区分缺失、空排期和解析故障 |
| 无新增后恢复前台 | 只读取批次/权限，不立即检查排片 | 明确产品语义并实现恢复策略 |
| macOS 从侧栏删最后订阅 | Timer 不立即重配 | 删除路径统一调度同步 |

这些为源码可见风险，不代表本轮已经通过实机稳定复现或自动化覆盖每一种交错。

## 8. 故障传播

排片 `refresh()` 捕获异常并保存 error，通常保留旧快照供页面显示。订阅检测没有相同的逐分组 catch，可能向调用者抛出；周期 Timer 的异步回调没有统一错误展示管道。

Worker 捕获顶层异常返回 false，但未把具体失败原因持久化供用户查看。启动插件初始化也缺少总的错误恢复页面。

通知异常被捕获而不记录：有利于不阻断应用内提醒，也降低了问题可观测性。不能从“没有日志报错”推断通知成功送达。

## 9. 超时、重试和限流

- HTTP：单请求 12 秒，目录分页不是全局 12 秒。
- 自定义原生通道：1 秒，通知权限流程不在这个范围内。
- 目录失败移除缓存，后续调用可重试。
- 网络失败没有指数退避、HTTP 429 专门处理或自适应限流。
- 系统任务重试由 WorkManager 执行，应用没有指定精确重试时间表。
- 不应为“更实时”盲目压低 Android 后台周期或增加全城扫描。

## 10. 建议观测指标

在后续实现中可优先增加：每轮触发来源、耗时、查询影院数、成功/失败数、新增场次数、最近成功检查时间、通知尝试结果和存储版本。

日志应保持本地或经用户明确同意导出，脱敏订阅偏好。性能数据应区分前台、后台、冷启动、图片下载和系统设置往返，避免把不同阶段混成一个平均数。

## 11. 优先优化顺序

先修数据正确性与错误隔离，再做列表虚拟化、缓存容量和并发查询。并发 HTTP 应有上限；在没有授权请求额度和压测依据时，不建议将所有影院无限 `Future.wait`。
